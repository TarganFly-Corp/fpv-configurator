# Правила роботи з історією Git

Документ описує, як команда FPV Configurator користується командами stash, rebase, patch (diff, format-patch, apply, am), cherry-pick і commit --amend. Правила обговорено на зустрічі команди на початку ЛР3, протокол зустрічі лежить у docs/Retro-LR3.md.

## Загальні правила

1. main захищена, зміни потрапляють туди лише через Pull Request з approve.
2. Переписувати історію (amend, rebase) можна тільки у своїй гілці. Історію main і чужих гілок не переписуємо.
3. Якщо переписана гілка вже була на GitHub, відправляємо її командою git push --force-with-lease. Звичайний --force не використовуємо: --force-with-lease відмовить, якщо хтось інший встиг додати коміт.
4. Перед будь-якою з команд нижче перевіряємо git status і git log --oneline --graph -10.

## git stash

Коли: треба терміново перемкнутися на іншу задачу (виправлення, рев'ю чужої гілки), а поточна робота ще не готова до коміту.

```powershell
git stash push -m "WIP: що саме відкладено"   # змінені відстежувані файли
git stash push -u -m "WIP: ..."               # разом з новими (невідстежуваними) файлами
git stash list                                # що лежить у сховку
git stash show -p 'stash@{0}'                 # переглянути зміни
git stash pop                                 # повернути зміни і прибрати запис зі сховку
git stash apply 'stash@{1}'                   # повернути, але запис залишити
git stash drop 'stash@{1}'                    # видалити запис
```

Правила: завжди пишемо повідомлення (-m), щоб через тиждень було зрозуміло, що це. Сховок не замінює коміт: якщо робота відкладається більше ніж на день, краще зробити WIP-коміт у своїй гілці. Після pop перевіряємо git stash list, щоб не лишалося забутих записів.

## git commit --amend

Коли: в останньому коміті помилка в повідомленні, забули додати файл або дрібно виправили код.

```powershell
git add забутий_файл
git commit --amend --no-edit            # додати файл, повідомлення не міняти
git commit --amend -m "нове повідомлення"
```

Правила: amend лише для коміту, якого ще немає на GitHub. Якщо коміт уже відправлено і гілка спільна, робимо новий коміт з виправленням.

## git rebase

Коли: main пішла вперед, а наша гілка створена від старої main. Перед відкриттям або оновленням PR перебазовуємо гілку, щоб історія була лінійною і PR містив лише наші коміти.

```powershell
git fetch origin
git rebase origin/main
# якщо конфлікт: виправити файл, потім
git add файл
git rebase --continue
# передумали:
git rebase --abort
git push --force-with-lease
```

Правила: після rebase обов'язково збираємо рішення і запускаємо dotnet test. Rebase не робимо на гілці, від якої вже створені гілки інших учасників, не попередивши їх.

## Патчі: git diff, git format-patch, git apply, git am

Коли: треба передати зміни іншому учаснику, не відправляючи їх на GitHub (зміни ще не готові для PR або треба показати пропозицію до чужої гілки). Патчі пересилаємо електронною поштою.

Відправник:

```powershell
git format-patch origin/main..HEAD -o ..\mail\<роль>-out\тема   # коміти, кожен окремим файлом
git diff --output=..\mail\<роль>-out\назва.patch               # незакомічені зміни
```

Далі лист з вебпошти: тема починається з [PATCH] (для кількох комітів [PATCH 0/N]), у тексті що і навіщо змінено, файли .patch вкладенням. Вміст патча в тілі листа не вставляємо: поштові програми переносять рядки і ламають патч.

Отримувач зберігає вкладення в ..\mail\<роль>-in\тема і накладає:

```powershell
git am (Get-ChildItem ..\mail\<роль>-in\тема\*.patch).FullName  # коміти з автором і повідомленням
git am --abort                                                     # якщо щось пішло не так
git apply --check ..\mail\<роль>-in\назва.patch                   # чи накладеться diff
git apply ..\mail\<роль>-in\назва.patch                           # накласти, коміт робить отримувач
```

Правила: патч з format-patch зберігає автора, тому в історії видно, чия це робота. Отримувач відповідає на лист: накладено чи ні і що змінив. Після того як зміни потрапили в гілку, файли патчів видаляємо з mail.

Git уміє надсилати патчі сам командою git send-email, але для неї потрібен SMTP-доступ до скриньки, а Proton дає його лише через окрему програму Proton Mail Bridge. Тому команда надсилає патчі вкладеннями з вебпошти.

## git cherry-pick

Коли: потрібен один або кілька конкретних комітів з іншої гілки, а не вся гілка. Наприклад, перенести виправлення в гілку релізу або взяти чужі тести, щоб відтворити дефект.

```powershell
git cherry-pick <хеш>
git cherry-pick -x <хеш>             # додати в повідомлення рядок «cherry picked from commit ...»
git cherry-pick A..B                 # коміти після A до B включно
# якщо конфлікт: виправити, git add, потім
git cherry-pick --continue
git cherry-pick --abort
```

Правила: у гілках релізу завжди використовуємо -x, щоб було видно, звідки взято виправлення. Cherry-pick створює новий коміт з новим хешем, тому git branch -d може вважати вихідну гілку незлитою. Перевіряємо це командою git cherry -v origin/main <гілка>: рядки з мінусом означають, що такі зміни в main уже є.

## Правила для тестувальника

1. Перед запуском тестів робоча копія має бути чистою. Експериментальні зміни (наприклад, тестові дані в catalog/custom-parts.json) відкладаємо в stash з повідомленням, а після перевірки повертаємо командою git stash apply.
2. Знайдений дефект спочатку закріплюємо червоним регресійним тестом у гілці test/..., потім створюємо Issue з міткою bug і посиланням на тест.
3. Розробник забирає регресійні тести у свою гілку виправлення через git cherry-pick, щоб відтворити дефект до виправлення.
4. Пропозицію виправлення коду тестувальник надсилає розробнику листом з патчем (git diff), а сам код у своїй гілці не комітить.
