# Правила роботи з історією Git

Документ описує, як команда FPV Configurator користується командами stash, rebase, patch (diff, format-patch, apply, am), cherry-pick і commit --amend. Правила обговорено на зустрічі команди на початку ЛР3, протокол зустрічі лежить у docs/Retro-LR3.md.

## Загальні правила

1. main захищена, зміни потрапляють туди лише через Pull Request з approve.
2. Переписувати історію (amend, rebase) можна тільки у своїй гілці. Історію main і чужих гілок не переписуємо.
3. Якщо переписана гілка вже була на GitHub, відправляємо її командою git push --force-with-lease. Звичайний --force не використовуємо: --force-with-lease відмовить, якщо хтось інший встиг додати коміт.
4. Перед будь-якою з команд нижче перевіряємо git status і git log --oneline --graph -10.

## git stash

Коли: треба терміново перемкнутися на іншу задачу (виправлення, рев'ю чужої гілки), а поточна робота ще не готова до коміту.

```powershell
git stash push -m "WIP: що саме відкладено"   # змінені відстежувані файли
git stash push -u -m "WIP: ..."               # разом з новими (невідстежуваними) файлами
git stash list                                # що лежить у сховку
git stash show -p 'stash@{0}'                 # переглянути зміни
git stash pop                                 # повернути зміни і прибрати запис зі сховку
git stash apply 'stash@{1}'                   # повернути, але запис залишити
git stash drop 'stash@{1}'                    # видалити запис
```

Правила: завжди пишемо повідомлення (-m), щоб через тиждень було зрозуміло, що це. Сховок не замінює коміт: якщо робота відкладається більше ніж на день, краще зробити WIP-коміт у своїй гілці. Після pop перевіряємо git stash list, щоб не лишалося забутих записів.

## git commit --amend

Коли: в останньому коміті помилка в повідомленні, забули додати файл або дрібно виправили код.

```powershell
git add забутий_файл
git commit --amend --no-edit            # додати файл, повідомлення не міняти
git commit --amend -m "нове повідомлення"
```

Правила: amend лише для коміту, якого ще немає на GitHub. Якщо коміт уже відправлено і гілка спільна, робимо новий коміт з виправленням.

## git rebase

Коли: main пішла вперед, а наша гілка створена від старої main. Перед відкриттям або оновленням PR перебазовуємо гілку, щоб історія була лінійною і PR містив лише наші коміти.

```powershell
git fetch origin
git rebase origin/main
# якщо конфлікт: виправити файл, потім
git add файл
git rebase --continue
# передумали:
git rebase --abort
git push --force-with-lease
```

Правила: після rebase обов'язково збираємо рішення і запускаємо dotnet test. Rebase не робимо на гілці, від якої вже створені гілки інших учасників, не попередивши їх.

## Патчі: git diff, git format-patch, git apply, git am

Коли: треба передати зміни іншому учаснику, не відправляючи їх на GitHub (зміни ще не готові для PR або треба показати пропозицію до чужої гілки). Патчі пересилаємо електронною поштою.

Відправник:

```powershell
git format-patch origin/main..HEAD -o ..\mail\<роль>-out\тема   # коміти, кожен окремим файлом
git diff --output=..\mail\<роль>-out\назва.patch               # незакомічені зміни
```

Далі лист з вебпошти: тема починається з [PATCH] (для кількох комітів [PATCH 0/N]), у тексті що і навіщо змінено, файли .patch вкладенням. Вміст патча в тілі листа не вставляємо: поштові програми переносять рядки і ламають патч.

Отримувач зберігає вкладення в ..\mail\<роль>-in\тема і накладає:

```powershell
git am (Get-ChildItem ..\mail\<роль>-in\тема\*.patch).FullName  # коміти з автором і повідомленням
git am --abort                                                     # якщо щось пішло не так
git apply --check ..\mail\<роль>-in\назва.patch                   # чи накладеться diff
git apply ..\mail\<роль>-in\назва.patch                           # накласти, коміт робить отримувач
```

Правила: патч з format-patch зберігає автора, тому в історії видно, чия це робота. Отримувач відповідає на лист: накладено чи ні і що змінив. Після того як зміни потрапили в гілку, файли патчів видаляємо з mail.

Git уміє надсилати патчі сам командою git send-email, але для неї потрібен SMTP-доступ до скриньки, а Proton дає його лише через окрему програму Proton Mail Bridge. Тому команда надсилає патчі вкладеннями з вебпошти.

## git cherry-pick

Коли: потрібен один або кілька конкретних комітів з іншої гілки, а не вся гілка. Наприклад, перенести виправлення в гілку релізу або взяти чужі тести, щоб відтворити дефект.

```powershell
git cherry-pick <хеш>
git cherry-pick -x <хеш>             # додати в повідомлення рядок «cherry picked from commit ...»
git cherry-pick A..B                 # коміти після A до B включно
# якщо конфлікт: виправити, git add, потім
git cherry-pick --continue
git cherry-pick --abort
```

Правила: у гілках релізу завжди використовуємо -x, щоб було видно, звідки взято виправлення. Cherry-pick створює новий коміт з новим хешем, тому git branch -d може вважати вихідну гілку незлитою. Перевіряємо це командою git cherry -v origin/main <гілка>: рядки з мінусом означають, що такі зміни в main уже є.

## Правила для тестувальника

1. Перед запуском тестів робоча копія має бути чистою. Експериментальні зміни (наприклад, тестові дані в catalog/custom-parts.json) відкладаємо в stash з повідомленням, а після перевірки повертаємо командою git stash apply.
2. Знайдений дефект спочатку закріплюємо червоним регресійним тестом у гілці test/..., потім створюємо Issue з міткою bug і посиланням на тест.
3. Розробник забирає регресійні тести у свою гілку виправлення через git cherry-pick, щоб відтворити дефект до виправлення.
4. Пропозицію виправлення коду тестувальник надсилає розробнику листом з патчем (git diff), а сам код у своїй гілці не комітить.

## Перегляд історії і обслуговування репозиторію (ЛР5)

Команди з практикуму ЛР5. Перші три допомагають розібратися, що і чому змінилося. Решта тримає репозиторій і робочі копії в порядку та потрібна під час випуску версії.

### git show

Коли: подивитися, що саме зробив коміт, тег або злиття, перед рев'ю чи перед тим, як брати коміт у реліз.

```cmd
REM останній коміт з усіма змінами
git show HEAD
REM лише список файлів і кількість рядків
git show --stat <хеш>
REM A додано, M змінено, D видалено, R перейменовано
git show --name-status <хеш>
REM повідомлення тега і коміт, на який він указує
git show v0.4-lr4
REM файл у тому вигляді, який він мав у версії
git show v0.4-lr4:docs/TZ.md
```

### git blame

Коли: рядок коду чи документа виглядає дивно або застарів, і треба знайти коміт і задачу, у межах якої його написано. Знайдений хеш далі відкриваємо через git show.

```cmd
REM лише рядки 20-30
git blame -L 20,30 шлях/до/файлу
git blame -L "/public BuildService(/,+6" FpvConfigurator.Services/BuildService.cs
REM повні дані коміту: автор, пошта, час, повідомлення
git blame -p -L 3,3 шлях/до/файлу
REM знайти рядки, перенесені з інших файлів
git blame -C шлях/до/файлу
```

Правила: blame показує, хто останнім змінив рядок, а не хто винен. Питання автору ставимо в Issue з хешем коміту.

### git mv і git rm

Коли: перенести, перейменувати або видалити файл, що вже є в репозиторії. Команди одразу заносять зміну в індекс, тому Git бачить перенесення як перейменування і не губить історію файлу.

```cmd
mkdir НоваПапка
git mv СтарийФайл.cs НоваПапка/СтарийФайл.cs
REM історія разом з часом до перенесення
git log --follow --oneline -- НоваПапка/СтарийФайл.cs
REM видалити з репозиторію і з диска
git rm файл
REM прибрати з індексу, файл на диску залишається
git rm --cached файл
```

Правила: перенесення робимо окремим комітом без змін вмісту файлів. Тоді git show показує R100 і рев'ю займає хвилину. Файл, доданий в індекс помилково, прибираємо через git rm --cached і дописуємо його шаблон у .gitignore.

### git clean

Коли: у робочій копії залишилися файли, яких немає в репозиторії: архіви, вивід тестів, розпаковані перевірки. Перед збіркою випуску робоча копія має бути чистою.

```cmd
REM що буде видалено (сухий запуск)
git clean -n
REM разом з невідстежуваними папками
git clean -n -d
REM видалити
git clean -f -d
REM також ігноровані bin і obj, але не .vs
git clean -n -d -x -e .vs
```

Правила: спочатку завжди -n. Ключ -x видаляє також файли з .gitignore, тобто результати збірки, після нього потрібен dotnet build. Папку .vs з налаштуваннями Visual Studio не чіпаємо (-e .vs).

### git fetch --prune і git prune

Коли: після злиття PR гілки на GitHub видалено, а в робочих копіях залишилися посилання origin/... і локальні гілки.

```cmd
REM прибрати origin/... для видалених на GitHub гілок
git fetch --prune
REM локальні гілки з позначкою gone
git branch -vv
REM видалити злиту локальну гілку
git branch -d назва
REM які недосяжні об'єкти буде видалено
git prune -n -v
git prune -v
REM стиснути сховище
git gc
```

Правила: на GitHub після злиття PR гілку видаляє тімлід. Гілки release/* і main не видаляються. git prune прибирає лише об'єкти, на які не посилається жоден коміт, гілка чи запис reflog, тому вже закомічена робота не губиться.

### git shortlog

Коли: підсумок ітерації або звіт: хто скільки комітів зробив.

```cmd
REM коміти за ЛР5 без комітів злиття
git shortlog -s -n --no-merges v0.4-lr4..HEAD
REM за весь час, з адресами
git shortlog -s -n -e HEAD
```

Один учасник може комітити під різними іменами і адресами (локально і через вебінтерфейс GitHub). Щоб shortlog не ділив його на кількох людей, у корені лежить файл .mailmap, у якому для кожної адреси записано одне ім'я.

### git verify-commit і git verify-tag

Коли: перевірити, що коміт або тег справді підписав той, кого вказано автором. Коміти злиття, створені кнопкою Merge pull request, GitHub підписує своїм ключем. Теги випусків тімлід підписує власним ключем GPG.

```cmd
REM підпис коміту
git verify-commit <хеш>
REM підписи останніх комітів
git log --show-signature -3
REM створити підписаний тег
git tag -s v0.5-lr5 -m "..."
REM перевірити підпис тега
git verify-tag v0.5-lr5
```

Ключі: відкритий ключ GitHub беремо з https://github.com/web-flow.gpg, ключ тімліда з https://github.com/targanfly.gpg. Обидва імпортуємо командою gpg --import.

### git archive

Коли: випуск версії. Архів містить файли рівно в тому стані, який зафіксовано тегом, без папки .git, без bin, obj і локальних файлів.

```cmd
git archive -o ..\fpv-configurator-0.5.zip --prefix=fpv-configurator-0.5/ v0.5-lr5
git archive --format=tar.gz -o ..\fpv-configurator-0.5.tar.gz --prefix=fpv-configurator-0.5/ v0.5-lr5
REM лише папка docs
git archive -o ..\fpv-configurator-0.5-docs.zip v0.5-lr5:docs
REM перелік файлів архіву
tar -tf ..\fpv-configurator-0.5.zip
```

Правила: архів робимо лише з тега, а не з робочої копії. Службові файли (.gitattributes, .gitignore, .mailmap) позначено в .gitattributes як export-ignore і в архів не потрапляють. Тестувальник перед випуском розпаковує архів в окрему папку і перевіряє, що рішення збирається і тести проходять.
