# Впровадження залежностей у FPV Configurator

Документ веде тімлід. Тут описано, який паттерн впровадження залежностей обрала команда, що показав аудит коду на початку ЛР4, які завдання рефакторингу поставлено і за якими правилами рев'юїмо код.

## 1. Обраний паттерн: впровадження через конструктор

Розглянуто три варіанти.

| Паттерн | Як клас отримує залежність | Плюси | Мінуси для нашого проєкту |
|---|---|---|---|
| Через метод (Setter injection) | властивість або метод SetX після створення об'єкта | можна замінити залежність під час роботи | об'єкт деякий час існує без залежності, про забутий виклик SetX дізнаємося лише з NullReferenceException; поле не може бути readonly |
| Через конструктор (Constructor injection) | параметри конструктора | без залежностей об'єкт не створити, компілятор нагадає про кожну; поля readonly; усі залежності видно в сигнатурі конструктора | при багатьох залежностях конструктор стає довгим (для нас це сигнал, що клас робить забагато) |
| Через інтерфейс (Interface injection) | клас реалізує інтерфейс на зразок IRegistryAware з методом Inject | контейнер сам знаходить, що впровадити | на кожну залежність потрібен окремий інтерфейс, а проблема «об'єкт без залежності» лишається така сама, як у setter |

Команда обрала впровадження через конструктор. Причини:

1. Усі залежності наших класів обов'язкові. JsonCatalogLoader без реєстру категорій або каталогу працювати не може, тому і створюватися без них не повинен.
2. Об'єкт після створення не змінюється: поля readonly, повторно впровадити іншу залежність не можна. Так менше станів, які треба тестувати.
3. Контейнер Microsoft.Extensions.DependencyInjection, яким користується Blazor (віха M6), підтримує саме цей паттерн. Те, що ми напишемо зараз, без змін підключиться до веб-застосунку.
4. Паттерн уже частково є в коді: ComponentFactory і JsonCatalogLoader отримують реєстр і фабрику через конструктор. Решту коду приводимо до того самого вигляду.
5. Для тестів досить створити об'єкт з потрібними аргументами. У ЛР4 це будуть справжні класи, у ЛР5 на їхнє місце стануть моки Moq, і код сервісів для цього міняти не доведеться.

## 2. Аудит коду (v0.3-lr3)

| Клас | Від чого залежить | Як отримує | Висновок |
|---|---|---|---|
| ParameterDefinition, ComponentCategory | ні від чого, крім власних даних | | незалежні |
| Frame, Motor, … CustomComponent | ComponentCategory (лише CustomComponent) | конструктор | незалежні, це об'єкти даних |
| CategoryRegistry | StandardCategories у статичному методі WithStandardCategories | статичні дані | незалежний, статичний метод лишаємо як зручний спосіб створення |
| ComponentCatalog | ні від чого | | незалежний, але інтерфейсу немає, тому інші класи можуть залежати лише від конкретного класу |
| ComponentFactory | ICategoryRegistry | конструктор | паттерн реалізовано правильно |
| JsonCatalogLoader | ICategoryRegistry, IComponentFactory, ComponentCatalog, файлова система | реєстр і фабрика через конструктор; каталог створює сам (new ComponentCatalog()); файл читає статичним File.ReadAllText | паттерн реалізовано частково: каталог прихований усередині методу |
| ICompatibilityRule | | | інтерфейс є, реалізацій немає. Немає і сервісу, який застосовує правила (ФВ-11…ФВ-14) |
| ManualCheck (Program) | усі класи | new у самій програмі | це корінь композиції, тут new дозволено, але порядок створення доводиться пам'ятати вручну |

## 3. Клас для тестування

Для тестування обрано JsonCatalogLoader. Він залежить від трьох інших класів проєкту: CategoryRegistry, ComponentFactory і ComponentCatalog. Зараз каталог він створює сам, тому тест не може передати свій каталог і перевірити, що саме туди потрапило. Після рефакторингу всі три залежності приходитимуть через конструктор у вигляді інтерфейсів, і в ЛР5 кожну з них можна буде замінити мок-об'єктом.

## 5. Правила рев'ю

Під час рев'ю PR тімлід перевіряє:

1. Клас, який щось робить (сервіс, завантажувач), отримує всі залежності через конструктор. Усередині такого класу немає new для інших сервісів чи правил.
2. Залежність оголошено як інтерфейс (ICategoryRegistry, IComponentCatalog, ICompatibilityRule), а не як конкретний клас.
3. Поля із залежностями readonly, конструктор перевіряє їх на null.
4. Немає «запасного» конструктора без параметрів, який сам створює залежності за замовчуванням. Такий конструктор повертає приховану залежність, від якої ми якраз позбуваємося.
5. Об'єкти створюються в одному місці, у корені композиції (AddFpvConfigurator). Програма і тести не дублюють порядок створення.
6. Незалежні класи (дані, правила) тестуються без підміни, залежні у ЛР5 з Moq.

## 7. Залежні і незалежні класи після рефакторингу

Розділ заповнює розробник. Незалежний клас не отримує інших сервісів проєкту, тому його тестують без підміни: створюють справжній об'єкт і викликають метод. Залежний клас отримує інші класи через конструктор у вигляді інтерфейсів. У ЛР5 замість них підставляються моки.

| Клас | Проєкт | Залежності (через конструктор) | Вид |
|---|---|---|---|
| ParameterDefinition, ComponentCategory | Core | немає | незалежний |
| Frame, FlightController, Esc, Motor, Propeller, Camera, Vtx, Battery | Components | немає | незалежні |
| CustomComponent | Components | ComponentCategory (дані, не сервіс) | незалежний |
| CategoryRegistry | Catalog | немає | незалежний |
| ComponentCatalog : IComponentCatalog | Catalog | немає | незалежний |
| ComponentFactory | Catalog | ICategoryRegistry | залежний |
| JsonCatalogLoader | Catalog | ICategoryRegistry, IComponentFactory, IComponentCatalog | залежний |
| Build | Services | немає | незалежний |
| StackMountRule, PropellerSizeRule, CellCountRule, VideoSystemRule | Services | немає | незалежні |
| BuildService | Services | IComponentCatalog, IEnumerable&lt;ICompatibilityRule&gt; | залежний |
| ServiceCollectionExtensions | Services | | корінь композиції |
